# 로컬 RAG 임베딩 적용 기록

이 문서는 OFFICESTRA의 로컬 임베딩 적용 과정을 네 단계로 기록한다.
운영 앱과 4317 백엔드는 이 작업 중 재시작하지 않는다.

## 1. 모델 선정

- 원본 모델: `BAAI/bge-m3`
- 로컬 실행 아티팩트: `onnx-community/bge-m3-ONNX`
- 고정 리비전: `25b9af8e87a38eb120cfe87125383677b9cd309e`
- 형식: ONNX Q8, 파일 크기 `568,479,395`바이트
- 출력 차원: 1,024
- 최대 문맥: 8,192토큰
- 라이선스: MIT
- 실행 위치: Apple M4 16GB, CPU ONNX Runtime, 외부 추론 API 없음

선정 근거:

- 한국어 검색 연구의 세 데이터셋에서 BGE-M3 dense 검색은
  KorQuAD `nDCG@10 0.785`, MrTyDi-ko `0.640`, MIRACL-ko `0.700`,
  평균 `0.708`로 보고됐다.
- ONNX와 Hugging Face tokenizer를 번들 Node에서 직접 실행해 별도
  Python이나 외부 추론 서비스가 필요 없다.
- 모델은 별도 워커 프로세스에서만 로드하고 유휴 5분 뒤 프로세스를
  종료해 모델 메모리를 완전히 반환할 수 있다.

M4 실측 (`dtype=q8`, 한국어 문장 4개):

- 최초 다운로드 포함 평가: `72.220초`
- 최종 직접 ONNX 워커의 캐시 검증·로드·4문장 임베딩 합계: `1.191초`
- 최대 RSS: `1,974,910,976`바이트 (`1.84GiB`)
- 출력: 4×1,024

모델 파일을 받는 과정 외에는 네트워크를 사용하지 않으며 입력 텍스트는
로컬 워커의 표준 IPC 밖으로 전송하지 않는다.

## 2. 스키마·최초 백필

- 신규 마이그레이션: `027_local_rag_embeddings.sql`
- `embedding`: `vector(1536)`에서 `vector(1024)`로 변경
- 추가 추적: `embedding_model`, `embedding_updated_at`,
  `embedding_error`
- HNSW 인덱스와 검색·위키 뷰를 같은 트랜잭션에서 재생성
- 임시 DB에서 최초 적용 1건, 재실행 적용 0건으로 이력 멱등성 확인

최초 백필 실측:

- 시작 문서: 1,695건
- 작업 중 새로 동기화된 문서를 포함한 최종 문서: 1,710건
- 완료: 1,710건, 누락 0건, 오류 0건, 모두 1,024차원·동일 모델
- 2건 배치 768건: `359.89초`; 진행 로그 700건 뒤 RSS를 확인해 중단 후 재개
- 1건 배치 942건: `370.70초`
- 총 실측 시간: `730.59초` (`12분 10.59초`)
- 순간 최대 워커 RSS: `2,620,456,960`바이트 (`2.44GiB`)
- 종료 직전 워커 RSS: `1,997,717,504`바이트 (`1.86GiB`)
- 백필 중 시스템 전체 메모리 여유: `74%`
- HNSW 인덱스 크기: `13MB`
- 종료 뒤 워커 프로세스: 0개
- 검증 중 추가된 업무 기록 7건도 두 번의 짧은 보충 백필로 처리해 현재
  1,717건 전부 임베딩 완료

업무 기록은 제목과 최종 결과가 검색 품질에 가장 중요하므로 입력을
192토큰으로 제한하고, 제목·본문 끝·본문 시작 순으로 구성했다. 가장 긴
원문은 106,692자였으나 모델 입력을 제한해 M4 CPU의 self-attention
메모리와 시간을 통제했다.

## 3. 실시간 적재·검색·임계값

- 모델은 백엔드가 아니라 별도 Node 워커 프로세스에서만 로드한다.
- 운영 유휴 제한은 `300,000ms`로 고정했다. 짧게 축소한 실제 모델
  검증에서 사용 직후 `active=true`, 제한 뒤 `active=false`, 남은 워커
  프로세스 0개를 확인했다.
- 모델 파일은 고정 리비전 URL에서 한 번 내려받고 크기·SHA-256을
  검증해 `~/.officestra/models`에 저장한다. 입력 텍스트는 로컬 IPC로만
  전달되며 외부 추론 API를 호출하지 않는다.
- 새 업무 기록의 RAG upsert가 끝난 뒤 즉시 임베딩한다. 실패하면
  `embedding_error`만 기록하고 완료 턴과 작업 기록은 그대로 유지한다.
  다음 백필은 `embedding IS NULL`인 행을 다시 처리한다.
- 내용이나 메타데이터가 바뀐 기존 기록은 예전 벡터를 NULL로 지워
  오래된 임베딩을 재사용하지 않는다.
- query만 있는 검색은 서버가 1,024차원 질문 벡터를 만든다. 모델이나
  벡터 조회가 실패하면 기존 PostgreSQL 전문검색으로 폴백한다.
- 기존 `embedding` 인자를 직접 보내는 경로는 별도로 유지한다.

10개 질의의 원시 벡터 점수를 비교해 최소 코사인 점수를 `0.45`로
정했다. 관련 결과 중 가장 낮은 1위는 "웹툰 그림 순서"의 `0.4661`이라
보존되며, `0.45` 아래의 약한 후보는 제거된다. 정확한 한 단어가 강하게
일치하는 ComfyUI·임베딩·터널은 전문검색 점수 `0.20` 이상일 때 정확
일치를 우선해 "터널"과 "터미널" 혼동을 막는다. 구분선 제목과 내용이
거의 없는 오타 기록도 검색 후보에서 제외한다.

## 4. 테스트·전후 비교

사용자가 제공한 기존 판정은 10건 중 정확 4·애매 4·헛다리 2였다.
새 검색의 1위 결과는 제목뿐 아니라 본문까지 열어 다음처럼 판정했다.

| 질의 | 새 검색 방식 | 새 1위 내용 | 점수 | 판정 |
|---|---|---|---:|---|
| 만화 콘티 | 벡터 | 두 표현이 같은 뜻이라는 RAG 설명 기록 | 0.4980 | 정확 |
| 웹툰 그림 순서 | 벡터 | 같은 RAG 설명 기록 | 0.4661 | 정확 |
| ComfyUI | 강한 정확 일치 | FaceDetailer·ComfyUI 설치 기록 | 0.3867 | 정확 |
| 그림 만드는 프로그램 | 벡터 | 이미지 생성→변형→영상 제작 파이프라인 | 0.5228 | 정확 |
| 임베딩 | 강한 정확 일치 | 임베딩 주기·방식 설명 | 0.3473 | 정확 |
| 검색이 잘 안 되는 문제 | 벡터 | 검색 API 문제 분석 | 0.6271 | 정확 |
| RAM 95% | 벡터 | RAM 고갈과 리소스 제한 조치 | 0.5315 | 정확 |
| 메모리 부족으로 중단 | 벡터 | VRAM 포화로 생성 중단 | 0.6442 | 정확 |
| 터널 | 강한 정확 일치 | SSH 터널 접속 인계 | 0.2651 | 정확 |

최종 검증:

- 백엔드: 376개 중 372 통과·환경 통합 4개 제외·실패 0
- Swift: 462개 통과·실패 0
- Release 앱 빌드와 `codesign --verify --deep --strict` 통과
- 패키지의 Node 24에서 ONNX 네이티브 모듈을 실제 로드해 1,024차원
  생성 및 유휴 뒤 워커 종료 확인

- 운영 앱·4317·launchctl 재시작 없음
