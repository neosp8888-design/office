# v1.3.1 release delay — 2026-08-10 KST

## Summary

The final artifacts were valid, but publishing took much longer than the final
build itself because two hosted-runner-only UI timing assumptions appeared one
after another. Each correction required a clean CI pass, and the second issue
was first exercised only after the release tag existed.

- From the first related CI failure to publication: **44 minutes 40 seconds**
  (`23:51:21` to `00:36:01` KST).
- From the first v1.3.1 candidate CI to publication: **28 minutes 08 seconds**
  (`00:07:53` to `00:36:01` KST).
- The final successful two-architecture release workflow itself: **9 minutes**.
- The normal observed path, including main CI, dispatch, and release: about
  **13 minutes 54 seconds**.
- The avoidable retry loop after the candidate CI: about **14 minutes 14
  seconds**, roughly half of the 28-minute candidate-to-publication interval.

No broken application or partial release was published. The failed release
created no GitHub Release assets.

## Root causes

1. `StreamingTextPacerTests` expected animation while inheriting a mutable
   system Reduce Motion value from the GitHub runner. The tests now set their
   SwiftUI accessibility environment explicitly.
2. `CachedLiveWorkspaceFeedsLifecycleTests` waited a fixed 4 milliseconds and
   then assumed the inner `NSScrollView` of an `NSHostingView` already existed.
   AppKit/SwiftUI mounting is asynchronous, especially under hosted-runner
   load. The test now polls the observable view hierarchy with a 500
   millisecond deadline.
3. The ordinary CI workflow and the release workflow did not exercise the same
   architecture conditions. Intel release testing began only after tagging,
   so the release workflow was acting as the first preflight for part of the
   matrix.

## Permanent prevention

- `Release UI Preflight` runs the two release-sensitive suites three times on
  arm64 and x86_64. Animation assertions set their Reduce Motion environment
  explicitly rather than attempting to change protected macOS preferences.
- `Community Preview Release` requires a successful preflight whose `head_sha`
  exactly equals the tag commit. It fails before dependency installation or
  packaging when the proof is absent. The preflight also requires its dispatch
  SHA, input SHA, checkout, and runner architecture to agree, preventing a
  neighboring commit from satisfying the gate.
- Release tags are created only after main CI and the exact-SHA preflight pass.
  Pushed release tags are immutable; a post-tag failure uses a new version.
- UI tests use explicit environment values and bounded condition polling, not
  fixed millisecond sleeps, for asynchronous view availability.
- Full architecture builds, app/DMG smoke tests, packaged-runtime Docker first
  tasks, checksum validation, and publication gates remain mandatory.

During local validation of the new three-pass preflight, the third pass exposed
one more fixed-time assertion in
`testTypingMountedAfterScrollStartPausesOnFirstLiveUpdate`. The product resumed
correctly, but the test checked only once after 120 milliseconds. That positive
resume assertion now uses monotonic, bounded condition polling for up to 500
milliseconds. This was corrected before enabling the new release gate.
